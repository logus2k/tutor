# Inform, Maintain, and Update Claude Configurations, Knowledge Sources, and Instructions

Setting up a Project, uploading knowledge, and writing instructions is a beginning, not an end. Configurations decay: documents are superseded, teammates change, policies are revised, and instructions written for last quarter quietly mislead this quarter. This topic tests whether you treat a Claude configuration as something that must be **owned, reviewed, and kept current** — and whether you recognize the general risk of stale configuration.

## Why maintenance is a first-class concern

Every part of a Claude setup is a snapshot of the moment it was written. A Project instruction that says "our fiscal year ends in March" was true when typed and may be false after a reorganization. An uploaded pricing sheet reflects the day it was uploaded. A connector was authorized for a project that may have ended months ago. None of these self-correct. Claude will confidently answer from whatever is in front of it, so *stale configuration produces stale-but-confident output* — one of the more insidious failure modes because nothing looks broken. The output is fluent and internally consistent; it is just wrong because the source is old.

This is the core judgment the exam rewards: recognizing that "I set it up once" is not the same as "it is correct now," and building a habit of verifying live state before relying on it.

## Keeping knowledge sources current

Uploaded files are static. When the underlying reality changes, the file does not — so maintenance means actively replacing it:

- **Replace superseded documents.** When a policy, contract, or price list is revised, upload the new version *and delete the old one* from Project knowledge. Leaving both is worse than leaving neither, because Claude may retrieve the outdated file — especially under RAG mode, where it selects passages from whatever is present.
- **Remove sources that no longer belong.** A knowledge base accumulates cruft: drafts, one-off references, files from a closed initiative. Prune them. A lean, current, well-labeled knowledge base retrieves more accurately than a large one full of contradictions.
- **Prefer connectors for living documents.** Where a source changes continuously, a connector that syncs to the latest version (as Google Drive does) beats a manual re-upload cycle that people inevitably forget. Choose the mechanism that matches how often the source changes.
- **Re-verify before high-stakes use.** Even a source you added yourself should be checked against the authoritative live version before you act on a compliance-sensitive or financial answer.

## Reviewing and updating instructions

Instructions drift more quietly than files because there is no "modified date" staring back at you. Treat them as living text:

- **Schedule a periodic review.** Read the profile and project instructions on a regular cadence — at natural checkpoints like a new quarter, a team change, or a shift in workflow. Ask of each line: is this still true, still needed, still non-contradictory?
- **Version deliberately when it matters.** claude.ai does not maintain a formal instruction changelog for you, so if a Project is important and shared, keep a lightweight record of what the instructions say and why — even a dated note in the Project description or a companion document. That gives you a way to answer "what changed and when did the behavior shift?"
- **Test after editing.** After changing instructions, run a representative prompt and confirm Claude now behaves as intended. An instruction edit is a claim about future behavior; verify it rather than assume it.
- **Prune conflicts.** As instructions accumulate over months, rules start to contradict each other and Claude has to guess. Removing an obsolete rule is as much maintenance as adding a new one.

## Reviewing connectors and access

Connectors and sharing are configuration too, and they carry data-access consequences that outlast the work they were set up for:

- **Audit connector scope periodically.** A Drive or Gmail connection authorized for one project may still be active long after. Review what is connected; disconnect what is no longer needed via **Customize > Connectors**. Reducing standing access is good hygiene.
- **Review project membership and permissions.** On Team and Enterprise plans, revisit who has **Can use** versus **Can edit** on shared Projects. People change roles and leave teams; edit rights on a widely-trusted Project should be held by a small, current set of maintainers, not everyone who once needed access.
- **Re-check data sensitivity.** A source that was fine to include when the Project was internal may not be once the Project is shared more broadly. Apply sensitivity controls to the *current* audience, not the original one.

## Ownership: the piece that makes maintenance actually happen

The most common real-world failure is diffuse responsibility: a shared Project that "everyone uses and no one maintains" degrades until people quietly stop trusting it. Assign a clear **owner** for each important configuration — a person accountable for keeping knowledge current, reviewing instructions, and managing access. Ownership is why the earlier advice to grant **Can edit** sparingly matters: a small maintainer group can keep a Project coherent, whereas universal edit rights produce unreviewed drift.

A practical operating rhythm looks like this:

1. **Inform** the team what a configuration is for and what's in it (the Project description and instructions do this).
2. **Maintain** on a cadence — prune stale files, review instructions, audit connectors and members.
3. **Update** deliberately — replace sources, edit instructions, then test the change and note it.

## Common pitfalls the exam probes

- **Trusting a configuration because it exists.** Its presence is not evidence it is current; verify against live reality before relying on it.
- **Adding without removing.** Uploading the new version while leaving the old one invites contradictory retrieval.
- **No owner.** A shared Project without an accountable maintainer decays and misleads.
- **Editing without testing.** An instruction change is unverified until you've run a prompt and seen the new behavior.
- **Forgotten access.** Connectors and edit permissions granted for finished work are standing risk until reviewed and revoked.

Maintaining a configuration is ultimately the same discipline as verifying any AI output: don't assume, re-check the live state, and keep the sources of truth genuinely true.
