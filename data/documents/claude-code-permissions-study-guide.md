# Claude Code: Permissions Reference

A study guide to Claude Code's permission system: the tiered baseline, the six modes, rule syntax and evaluation order, per-tool rule semantics, auto mode's classifier, protected paths, workspace trust, and managed policy.

Verified against code.claude.com/docs/en/permissions and /permission-modes.

---

## 1. The mental model

Four mechanisms decide whether a tool call runs, and they are **not** interchangeable:

| Mechanism | Question it answers | Where configured |
|---|---|---|
| **Tool availability** | Can Claude see and request this tool at all? | `--tools`, bare-name deny rules, subagent `tools:` |
| **Permission mode** | What is the default answer when nothing else matches? | `defaultMode`, `--permission-mode`, `Shift+Tab` |
| **Permission rules** | Is this specific call allowed, prompted, or blocked? | `permissions.allow` / `.ask` / `.deny` |
| **Hooks** | Runtime logic evaluating the actual call | `PreToolUse`, `PermissionRequest` |

Plus **sandboxing**, which is OS-level and applies only to Bash and its children.

**The single most important sentence in the docs on this subject:** permission rules are enforced by Claude Code, **not by the model**. Instructions in your prompt or CLAUDE.md shape what Claude *tries* to do; they do not change what Claude Code *allows*. To grant or revoke access you need `/permissions`, rules, a mode, or a hook.

### The tiered baseline

| Tool type | Example | Approval required | "Yes, don't ask again" |
|---|---|---|---|
| Read-only | File reads, Grep | No, within the working directory and additional directories | N/A |
| Bash commands | Shell execution | Yes, except a built-in read-only set | **Permanently, per repository and command** |
| File modification | Edit/write | Yes | **Until session end only** |

That asymmetry catches people: a Bash approval persists, a file-edit approval does not.

Permanent approvals are saved to `.claude/settings.local.json` **at the git repository root**, resolved through worktrees to the main checkout, so the rule applies anywhere in that repository including subdirectories and worktrees. Outside a git repository, or when the repo root is your home directory, it saves in the starting directory instead. (Before v2.1.211 it always saved in the starting directory, so worktree approvals did not propagate. Old rules saved that way still apply where they are.)

### Ctrl+E on a permission prompt

On a Bash or PowerShell prompt, `Ctrl+E` shows an explanation: what the command does, why Claude is running it, what could go wrong, labeled **Low risk**, **Med risk**, or **High risk**. The explanation is generated by a model request made **only when you press Ctrl+E**, not on every prompt, and showing it does not run the command. Disable with `permissionExplainerEnabled: false` in `~/.claude.json`.

## 2. Permission modes

| Mode | Runs without asking | Best for |
|---|---|---|
| `default` | Reads only | Getting started, sensitive work |
| `acceptEdits` | Reads, file edits, common filesystem commands | Iterating on code you review after |
| `plan` | Reads, plus classifier-approved commands when auto mode is available | Exploring before changing |
| `auto` | Everything, with background safety checks | Long tasks, prompt fatigue |
| `dontAsk` | Only pre-approved tools | Locked-down CI and scripts |
| `bypassPermissions` | Everything | Isolated containers and VMs only |

**Naming.** The mode that reviews every action is labeled **Manual** in the CLI, `--help`, the VS Code and JetBrains extensions, and the desktop app. Its config value is `default`, which is what hooks and SDK integrations use. `manual` is accepted as an alias from v2.1.200.

### What applies in every mode, including bypassPermissions

- `deny` rules and explicit `ask` rules (though neither can block `EndConversation` while any other tool remains)
- Connector tools your organization set to `ask`
- MCP tools marked `requiresUserInteraction`
- The `rm -rf /` and `rm -rf ~` circuit breaker

**Allow rules have no effect in `bypassPermissions`**, because everything else is already approved.

### Switching modes

`Shift+Tab` cycles `default` → `acceptEdits` → `plan`. Beyond that:

- `auto` appears when your account meets the requirements; cycling to it needs no confirmation
- `bypassPermissions` appears only after you start with `--permission-mode bypassPermissions`, `--dangerously-skip-permissions`, `--allow-dangerously-skip-permissions`, or `defaultMode: "bypassPermissions"`. The `--allow-` variant adds it to the cycle **without activating it**
- `dontAsk` **never appears in the cycle**; set it with `--permission-mode dontAsk`

Enabled optional modes slot in after `plan`, with `bypassPermissions` first and `auto` last.

Status bar badges: `⏸ manual mode on` (gray, v2.1.203+), `⏵⏵ accept edits on`, `⏸ plan mode on`, `⏵⏵ auto mode on`, `⏵⏵ don't ask on`, `⏵⏵ bypass permissions on`.

### acceptEdits specifics

Beyond file edits, it auto-approves these Bash commands: `mkdir`, `touch`, `rm`, `rmdir`, `mv`, `cp`, `sed`. Also when prefixed with safe env vars (`LANG=C`, `NO_COLOR=1`) or process wrappers (`timeout`, `nice`, `nohup`).

**Only for paths inside the working directory or `additionalDirectories`.** Paths outside that scope, protected-path writes, and all other Bash commands still prompt.

With the PowerShell tool enabled, it also auto-approves `Set-Content`, `Add-Content`, `Clear-Content`, and `Remove-Item` on in-scope paths, plus common aliases.

### Plan mode specifics

Claude reads, explores with shell commands, and writes a plan without editing source. Edits stay blocked until you approve the plan, **except in sessions with bypass permissions available**, where plan-mode blocks are not enforced at all.

As of v2.1.218, when auto mode is available and `useAutoModeDuringPlan` is on (the default), the classifier reviews shell commands during planning instead of prompting you.

Plan approval options:

- **Yes, and use auto mode** (reads "Yes, auto-accept edits" when auto mode is unavailable, or "Yes, and bypass permissions" in bypass sessions)
- **Yes, manually approve edits**
- **No, refine with Ultraplan on Claude Code on the web**
- **No, keep planning**

`Ctrl+G` opens the plan in your editor before Claude proceeds. Approving also **names the session** from the plan content, unless you set a name with `--name` or `/rename`.

### dontAsk specifics

Auto-denies every call that would otherwise prompt. Claude runs only: `permissions.allow` matches, built-in read-only Bash commands, and calls approved by a PreToolUse hook. The session never waits for input.

It **denies** rather than prompts for: explicit `ask` rule matches, `AskUserQuestion`, connector tools set to `ask`, and MCP tools marked `requiresUserInteraction` — even if your allow rules match them.

### bypassPermissions specifics

Skips prompts **including writes to protected paths** (since v2.1.126).

Safeguards that remain: explicit `ask` rules, org-`ask` connector tools, `requiresUserInteraction` MCP tools, and root/home removals. As of v2.1.208 the removal circuit breaker also fires when the command contains command substitution (`$(...)`, backticks) or process substitution (`<(...)`), whether the removal sits inside the substitution or elsewhere in the command.

Entry constraints:

- **You cannot enter it from a session started without it enabled.** It must be enabled at launch
- First interactive use shows a responsibility dialog, saved to user settings so it appears once. Declining exits
- Non-interactive mode shows no dialog, and `--bg` sessions are **refused** until you have accepted it interactively
- On Linux and macOS, Claude Code **refuses to start as root or under sudo**: `--dangerously-skip-permissions cannot be used with root/sudo privileges for security reasons`. The check is skipped inside a recognized sandbox
- Claude Code on the web ignores `defaultMode: "bypassPermissions"` and `"dontAsk"` from settings, so a repo cannot start a cloud session in bypass mode

Block it organizationally with `permissions.disableBypassPermissionsMode: "disable"`. It works from any scope, so a user can also lock themselves out.

## 3. Rule syntax and evaluation

### Evaluation order

**deny → ask → allow. First match wins. Specificity does not change the order.**

Two consequences that surprise people:

1. A broad deny like `Bash(aws *)` blocks calls that also match a narrower allow like `Bash(aws s3 ls)`. **A deny rule cannot carry allowlist exceptions.**
2. The same holds between ask and allow: a matching `ask` prompts even when a more specific `allow` matches.

### Bare names versus scoped patterns in deny rules

| Form | Effect |
|---|---|
| `Bash` (bare) | **Removes the tool from Claude's context entirely.** Claude never sees it |
| `Bash(rm *)` (scoped) | Tool stays available; matching calls are blocked when attempted |

`Bash(*)` is equivalent to bare `Bash` and also removes the tool. Bare-name removal applies to every tool **except `EndConversation`**: a deny cannot remove it while any other tool remains, and an ask never prompts for it.

### Basic forms

```json
{
  "permissions": {
    "allow": ["Bash(npm run *)", "Read(/docs/**)"],
    "ask": ["Bash(git push *)"],
    "deny": ["Read(./.env)", "WebFetch(domain:paste.example)"]
  }
}
```

### Match by input parameter

Deny and ask rules can match a top-level input parameter on any tool with `Tool(param:value)`.

| Rule | Matches |
|---|---|
| `Agent(model:opus)` | Agent calls requesting the Opus tier |
| `Agent(isolation:worktree)` | Agent calls requesting a worktree |
| `Bash(run_in_background:true)` | Backgrounded Bash calls |

Rules for parameter matching:

- **Allow rules cannot use this form.** Matching one parameter would not establish the call is safe overall
- The parameter must be a **direct field** of the tool's input. Nested fields are not matchable
- **One parameter per rule.** Write two rules rather than combining
- `*` wildcards the value; without it the match is exact
- **An omitted parameter is never matched**, so `Agent(model:*)` does not match a call that leaves `model` unset
- The value compares against **the literal input Claude sends, before normalization**. `Agent(model:opus)` matches the alias but not a full model ID. Use `--verbose` to see exact parameter names and values

**You cannot match a tool's primary content field this way**: `command` (Bash, PowerShell), `file_path` (Read, Edit, Write), `path` (Grep, Glob), `notebook_path` (NotebookEdit), `url` (WebFetch). A rule like `Bash(command:rm *)` would be bypassable by a compound command, so Claude Code ignores it and warns at startup.

### Tool-name wildcards

Deny and ask rules accept globs in the tool-name position, matching the **full** name. `"*"` matches every tool; `"mcp__*"` matches every MCP tool. A tool matched by a bare-name glob deny is removed from context, with the same `EndConversation` exception.

**Allow rules accept tool-name globs only after a literal `mcp__<server>__` prefix**, and the server segment must be glob-free. `mcp__puppeteer__*` works; `mcp__github__get_*` works. An unanchored allow glob such as `"*"`, `"B*"`, or `"mcp__*"` is **skipped with a warning** and auto-approves nothing.

### Startup warnings and canonical names

A deny or ask rule whose tool name matches no known tool produces a startup warning to catch typos. Names containing `_` or `*` are exempt.

**The label in the transcript can differ from the canonical name.** The tool labeled `Stop Task` is canonically `TaskStop`. Rules and hook matchers match the canonical name only. Use the tools reference for canonical names.

## 4. Per-tool rule semantics

### Bash

Wildcards work at any position:

```
Bash(npm run build)     exact command
Bash(npm run test *)    prefix
Bash(npm *)             any npm command
Bash(* install)         any command ending in " install"
Bash(git * main)        git checkout main, git log --oneline main, git push origin main
```

A single `*` spans spaces, so one wildcard can cover multiple arguments.

**The space before `*` is a word boundary.** `Bash(ls *)` matches `ls -la` but not `lsof`. `Bash(ls*)` matches both. The `:*` suffix is equivalent to a trailing ` *`, and is **only recognized at the end**: in `Bash(git:* push)` the colon is a literal character.

#### Compound commands

Claude Code is shell-operator aware. Separators recognized: `&&`, `||`, `;`, `|`, `|&`, `&`, and newlines. **A rule must match each subcommand independently**, so `Bash(safe-cmd *)` does not permit `safe-cmd && other-cmd`.

Approving a compound command with "don't ask again" saves **a separate rule per subcommand** that required approval, up to 5. Approving `git status && npm test` saves a rule for `npm test`, so it is recognized regardless of what precedes it. A `cd` into a subdirectory generates its own Read rule.

#### Wrappers

Claude Code strips a fixed, **non-configurable** set of wrappers before matching, so `Bash(npm test *)` also matches `timeout 30 npm test`:

`timeout`, `time`, `nice`, `nohup`, `stdbuf`, the shell builtins `command` and `builtin`, and zsh's `noglob`.

Not stripped: the query form `command -v`, and zsh's `nocorrect`.

Leading assignments of **known-safe** environment variables are stripped, so `Bash(npm test *)` matches `NODE_ENV=test npm test`. An allow rule will not match past any other variable's assignment. **A deny or ask rule matches past any leading assignment**, so `Bash(rm *)` in deny still catches `FOO=bar rm -rf tmp/`.

Bare `xargs` is stripped, so `Bash(grep *)` matches `xargs grep pattern`. **Only when flagless**: `xargs -n1 grep pattern` is matched as an `xargs` command.

**The dangerous gap.** Environment runners are *not* in the strip list: `direnv exec`, `devbox run`, `mise exec`, `npx`, `docker exec`. Because they execute their arguments, `Bash(devbox run *)` matches **whatever comes after `run`**, including `devbox run rm -rf .`. Write rules that include both the runner and the inner command: `Bash(devbox run npm test)`, one per inner command.

Exec wrappers `watch`, `setsid`, `ionice`, and `flock` always prompt and cannot be prefix-approved. Same for `find` with `-exec` or `-delete`: a `Bash(find *)` rule does not cover those forms.

#### Read-only commands

A built-in, **non-configurable** set runs without prompting in every mode: `ls`, `cat`, `echo`, `pwd`, `head`, `tail`, `grep`, `find`, `wc`, `which`, `diff`, `stat`, `du`, `cd`, and read-only forms of `git`. To require a prompt for one, add an `ask` or `deny` rule.

Unquoted globs are permitted for commands whose every flag is read-only (`ls *.ts`, `wc -l src/*.py`).

Still prompts:

- **Unquoted globs with write-capable flags**: `find`, `sort`, `sed`, `git` prompt, because the glob could expand to something like `-delete`
- **`docker` pointed at another daemon**: flags like `-H`, `--context`, Podman's `--url`/`--connection`
- **`file` with `-m`/`--magic-file` or `-f`/`--files-from`**, since those open paths named in the flag value
- **Windows UNC paths** (`\\server\share\file`), because accessing one can send your Windows credentials to that host. Also applies to PowerShell
- **Unparseable commands**, and anything longer than 10,000 characters

`cd` into your working directory or an additional directory is read-only, and `cd packages/api && ls` runs unprompted when each part qualifies. Two combinations prompt anyway:

- **`cd` + `git`**, when the `cd` changes directory, since git in a new directory can execute that directory's hooks. A no-op `cd` does not trigger it
- **`cd` + output redirect**, when the redirect target's resolution is ambiguous after the `cd`. `/dev/null` targets do not prompt

#### The argument-constraint warning

Bash patterns that try to constrain arguments are fragile. `Bash(curl http://github.com/ *)` fails against: options before the URL, a different protocol, redirects, variables (`URL=... && curl $URL`), and extra spaces.

More reliable approaches: deny `curl`/`wget` and use WebFetch with domain rules; use a PreToolUse hook that validates URLs; or put guidance in CLAUDE.md **paired with** one of the above, since CLAUDE.md shapes intent without enforcing a boundary.

**WebFetch rules alone do not prevent network access.** If Bash is allowed, Claude can reach any URL with curl.

### PowerShell

Same shape as Bash. Wildcards at any position, `:*` suffix equivalent, bare `PowerShell` matches everything.

Two differences: **common aliases are canonicalized**, so `PowerShell(Get-ChildItem *)` matches `gci`, `ls`, and `dir`; and **matching is case-insensitive**. Claude Code parses the PowerShell AST, splitting on `|`, `;`, and on PS7+ `&&` and `||`. Every subcommand must match.

### Read and Edit

`Edit` rules apply to **all built-in file-editing tools**. `Read` rules apply best-effort to all file-reading tools including Grep and Glob, to `@file` mentions, and to IDE selection and open-file context.

Two version-gated behaviors:

- **v2.1.208+**: a `Read` deny also blocks the **Edit** tool on that path, including creating a new file there. Write and NotebookEdit are not covered, so add an `Edit` deny for paths no tool may change
- **v2.1.210+**: file permissions are checked against **`Edit(path)` and `Read(path)` rules only**. A path rule for `Write`, `NotebookEdit`, `Glob`, or legacy `MultiEdit` is accepted but never consulted, with a startup warning. Use `Edit(docs/**)` not `Write(docs/**)`; use `Read(docs/**)` not `Glob(docs/**)`. A tool-name rule with no path, such as a bare deny for `Write`, still matches at the tool level

Both use **gitignore pattern syntax** with four anchor types:

| Pattern | Meaning | Example resolves to |
|---|---|---|
| `//path` | Absolute from filesystem root | `/Users/alice/secrets/**` |
| `~/path` | From home directory | `/Users/alice/Documents/*.pdf` |
| `/path` | **Relative to the settings source** | `<project root>/src/**/*.ts` in project settings |
| `path` or `./path` | Relative to current directory | `<cwd>/*.env` |

**The single leading slash is the classic trap.** `/Users/alice/file` is *not* absolute; it anchors at the settings source. Use `//Users/alice/file`.

Where `/path` anchors, by settings source:

| Rule defined in | `/path` resolves to |
|---|---|
| `.claude/settings.json` | `<project root>/path` |
| `.claude/settings.local.json` | `<original cwd>/path` |
| `~/.claude/settings.json` | `~/.claude/path` |
| `--settings <file>` | `<directory of file>/path` |
| CLI flags, `/permissions`, session rules | `<original cwd>/path` |

So `Read(/secrets/**)` in **user settings** blocks `~/.claude/secrets/**`, not a project `secrets` directory. For a user-settings rule that applies inside every project, use `//` or `~/`.

On Windows, paths normalize to POSIX: `C:\Users\alice` becomes `/c/Users/alice`. Use `//c/**/.env` for one drive, `//**/.env` across all.

**Matching depth differs by rule type** for single-segment directory patterns:

| Rule | Matches `src/app.ts` | Matches `vendor/pkg/src/lib.js` |
|---|---|---|
| `Edit(src/**)` as **allow** | Yes | No |
| `Edit(src/**)` as **deny or ask** | Yes | **Yes** |
| `Edit(/src/**)` any type | Yes | No |
| `Edit(**/src/**)` any type | Yes | Yes |

Bare filenames follow gitignore semantics and match at any depth: `Read(.env)` and `Read(**/.env)` are equivalent.

**Symlinks** check two paths, the link and its target, treated asymmetrically:

- **Allow rules** apply only when **both** match. A symlink inside an allowed directory pointing outside it still prompts
- **Deny rules** apply when **either** matches

So with `Read(./project/**)` allowed and `Read(~/.ssh/**)` denied, a symlink at `./project/key` pointing to `~/.ssh/id_rsa` is blocked.

**The enforcement boundary.** Read and Edit deny rules apply to built-in file tools and to file commands Claude Code recognizes in Bash (`cat`, `head`, `tail`, `sed`). They **do not** apply to arbitrary subprocesses that read or write files indirectly, like a Python or Node script. For OS-level enforcement across all processes, enable the sandbox.

When you approve a path with "don't ask again", Claude Code escapes gitignore metacharacters (`[`, `]`, `*`) so the rule matches only the literal path. Rules you write yourself are not escaped.

### WebFetch

Rules use `domain:` and match the hostname. Case-insensitive, `*` supported, trailing `.` stripped from both sides.

- `WebFetch(domain:example.com)` matches that host
- `WebFetch(domain:*.example.com)` matches any subdomain at any depth, **but not `example.com` itself**
- `WebFetch(domain:*)` equals a bare `WebFetch` rule

**Wildcards other than a leading `*.` or a bare `*` match only between two dots.** `WebFetch(domain:example.*)` matches `example.org` but **not** `example.evil.com`, since `*` would have to cross a dot. This is deliberate: it stops a trailing wildcard from matching attacker-registrable domains.

### MCP

- `mcp__puppeteer` matches any tool from that server
- `mcp__puppeteer__*` same, wildcard form
- `mcp__puppeteer__puppeteer_navigate` one tool

Connector tools appear as `mcp__claude_ai_<server>__<tool>`. If your org set a connector tool to `ask`, **allow rules for it do not take effect**: it prompts in every mode including auto and bypass, and is denied in `dontAsk`.

### Agent

`Agent(Explore)`, `Agent(Plan)`, `Agent(my-custom-agent)`. Add to `deny` or use `--disallowedTools` to disable specific subagents.

### Cd

Controls where `/cd` can move the session. **`Cd` is not a model-invocable tool**: Claude cannot call it, and rules apply only when you run `/cd` yourself.

- Bare `Cd` deny disables `/cd` entirely
- `Cd(<pattern>)` deny blocks matching targets, checking **every spelling including each symlink hop**
- **Adding any `Cd` allow rule switches `/cd` to allowlist mode**: the resolved target must match, or `/cd` refuses
- With no `Cd` rules, `/cd` prompts you to trust unfamiliar directories

Path patterns share the `//`, `~/`, `/` anchors but match **against the whole directory path, not gitignore-style**: `*` matches exactly one segment, `**` matches across segments, and a trailing `/**` also matches its named root.

| Rule | Matches | Does not match |
|---|---|---|
| `Cd(~/code/*)` | `~/code/app` | `~/code/app/src`, `~/code` |
| `Cd(~/code/**)` | `~/code` and anything under it | outside `~/code` |
| `Cd(**/node_modules)` | any `node_modules` at any depth | `node_modules/pkg` |

## 5. Auto mode

A separate classifier model reviews actions before they run, blocking anything that escalates beyond your request, targets unrecognized infrastructure, or looks driven by hostile content Claude read.

Auto mode also nudges Claude to keep working without stopping for clarifying questions. For stronger autonomous behavior **while keeping** permission prompts, use the Proactive output style instead.

**The docs' own caveat:** auto mode reduces prompts but does not guarantee safety. Use it where you trust the general direction, not as a replacement for review on sensitive operations.

### Availability requirements

All must hold:

- **Plan**: all plans
- **Organization**: available by default on Team and Enterprise; admins disable with `permissions.disableAutoMode: "disable"` in managed settings
- **Model**: on the Anthropic API and Claude Platform on AWS, Opus 4.6+, Sonnet 4.6+, or Fable 5. On Bedrock, Google Cloud's Agent Platform, Microsoft Foundry, and signed-in gateway sessions, only Sonnet 5, Opus 4.7+, and Fable 5. Sonnet 4.5, Opus 4.5, Haiku, and claude-3 are unsupported everywhere
- **Provider**: available by default on all of the above (the `CLAUDE_CODE_ENABLE_AUTO_MODE=1` requirement was removed in v2.1.207)

"Auto mode unavailable" means a requirement is unmet, not a transient outage. A message naming a model and saying it "cannot determine the safety" of an action means a **classifier request failed**, which is usually transient.

**`defaultMode: "auto"` is ignored in `.claude/settings.json` and `.claude/settings.local.json`** as of v2.1.142, so a repository cannot grant itself auto mode. Put it in `~/.claude/settings.json`.

### Decision order inside auto mode

1. Your allow, ask, and deny rules resolve immediately — **except** that protected-path writes route to the classifier even when an allow matches, org-`ask` connector tools and `requiresUserInteraction` MCP tools prompt directly even when an allow matches, and content-scoped ask rules fall back to a prompt
2. Read-only actions and working-directory file edits are auto-approved, except protected-path writes
3. Everything else goes to the classifier
4. On a block, Claude receives the reason and tries an alternative. In most sessions the reason is the fixed text `Blocked by classifier` rather than an explanation (v2.1.208+)

**On entering auto mode, broad allow rules granting arbitrary code execution are dropped**: blanket `Bash(*)` / `PowerShell(*)`, wildcarded interpreters like `Bash(python*)`, package-manager run commands, and `Agent` allow rules. Narrow rules like `Bash(npm test)` carry over. Dropped rules are restored on exit.

**What the classifier sees**: user messages, tool calls, and your CLAUDE.md. **Tool results are stripped**, so hostile file or web content cannot manipulate it directly. A separate server-side probe scans incoming tool results and flags suspicious content before Claude reads it.

### Trust boundary

The classifier trusts your working directory and the remotes configured for it **when the session started**. A remote added or repointed mid-session with `git remote add` or `set-url` is **not** trusted (v2.1.200+). Everything else is external until you configure trusted infrastructure.

### Blocked by default (representative, not exhaustive)

Baseline: downloading and executing code (`curl | bash`), sending sensitive data to external endpoints, production deploys and migrations, mass cloud-storage deletion, granting IAM or repo permissions, modifying shared infrastructure, irreversibly destroying pre-existing files, force push, `terraform destroy` and equivalents.

Git-specific: `git reset --hard`, `git checkout -- .`, `git restore .`, `git clean -fd`, `git stash drop`/`clear`, and `git commit --amend` on a commit not created in this session or already pushed. A message-only reword of a session-created commit is allowed.

Added in v2.1.195+: writing to a secret manager, changing DNS or TLS certs, merging an unapproved PR or approving Claude's own, disabling CI checks, automation-command comments (`atlantis apply`), production feature-flag changes, protected IaC scopes, cluster node drains, over-broad cluster writes (`--all`, label selectors), DaemonSets and admission webhooks, interactive shells or port-forwards into sensitive targets, public tunnels and reverse shells, printing live credentials, sensitive data locations, routing package installs around an internal registry, safety-disarming flags like `--insecure`, launching autonomous agent loops without approval or sandbox, and Chrome actions that could send page content off-origin.

Added in v2.1.198+: wildcard/glob/age-filter deletion in shared scratch directories, sending sensitive details to recipients your message did not authorize, and sending keystrokes to Claude Code's own tmux pane.

Added in v2.1.200+: disabling security-guarding tests, deleting stateful resources Claude did not create, repointing API base URLs or registry mirrors at unrelated third-party hosts (including in `.env.example`), changing push destinations, pushing secrets to public repos, and opening PRs against a different repository or organization.

Added in v2.1.203+: content from sensitive local stores (transcripts, SSH keys, cloud credentials, browser profiles, shell history) entering a commit, push, PR, gist, or package publish. **The repository being private does not clear this.**

Added in v2.1.205+: **writing to Claude Code's own session transcripts** under `~/.claude/projects/`, directly or via shell. Reading is not blocked. Also recursive forced deletes whose target is an unassigned shell variable, since the classifier cannot verify the target from conversation alone.

### Allowed by default

Local file operations in the working directory, installing dependencies from lock files and manifests, reading `.env` and sending credentials to their matching API, read-only HTTP.

v2.1.195+: deleting jobs Claude created this session, reading and writing security-related code as part of your task, inter-agent messages, and sending data to trusted domains in `autoMode.environment` (data flow only, not destructive or credential operations).

v2.1.211+: **pushing to any branch of the repository you are working in, including the default branch.** Exceptions: a non-default branch named like a deploy target (`production`, `gh-pages`) is judged on its own terms; content is still checked against other rules; `permissions.deny` still blocks specific branches in every mode; remote branch protection still applies.

### Boundaries stated in conversation

Telling Claude "don't push" or "wait until I review" is treated as a **block signal**, and the classifier blocks matching actions even when defaults would allow them. A boundary stays in force until you lift it. **Claude's own judgment that a condition was met does not lift it.**

But: boundaries are **not stored as rules**. The classifier re-reads them from the transcript each check, so a boundary can be **lost to context compaction**. For a hard guarantee, use a deny rule.

### Fallback thresholds

Denied actions show a notification and appear in `/permissions` under **Recently denied**, where `r` retries with manual approval.

**3 consecutive blocks or 20 total** pause auto mode and resume prompting. Approving the prompted action resumes auto mode. **Not configurable.** Any allowed action resets the consecutive counter; the total counter persists for the session.

In `-p` mode, repeated blocks abort the session since there is nobody to prompt.

### Subagents under auto mode

Three checkpoints:

1. **Before spawn**: the delegated task description is evaluated (v2.1.178+)
2. **During**: each action goes through the classifier with the parent's rules, and **any `permissionMode` in the subagent's frontmatter is ignored**
3. **On completion**: the classifier reviews the full action history; concerns prepend a security warning to the results

### Cost and latency

The classifier runs on **Claude Sonnet 5 by default**, not your `/model` selection (v2.1.210+). A server-side configured model takes precedence. Falls back to the session model when that is Sonnet 4.6 or when `availableModels` excludes Sonnet 5, or to an Opus model when the session runs Fable 5.

Classifier calls **count toward your token usage**. Reads and working-directory edits skip the classifier, so overhead comes mainly from shell and network operations. Sandbox network verdicts are cached per host and port: an allow lasts until new content enters the conversation, a deny is dropped at turn end interactively but reused for the whole run in `-p` and SDK sessions, and any mode or rule change drops all cached verdicts.

### Configuration

`claude auto-mode defaults` prints the full rule lists as JSON; `--label <prefix>` filters. `claude auto-mode config` shows your effective config. `claude auto-mode reset` removes the `autoMode` section from user settings.

The `autoMode` settings key holds `environment`, `allow`, `soft_deny`, and `hard_deny` arrays of prose rules. Include the literal `"$defaults"` in an array to inherit built-ins at that position. **Read only from user settings, `--settings`, and managed settings** — ignored in project and local settings.

`autoMode.classifyAllShell: true` (v2.1.193+) suspends every Bash and PowerShell allow rule while auto mode is active, routing all shell commands through the classifier.

## 6. Protected paths

Writes here are **never auto-approved**, except in `bypassPermissions` and in planning sessions with bypass available.

| Mode | Protected-path writes |
|---|---|
| `default`, `acceptEdits` | Prompted |
| `plan` | Prompted; allowed with bypass available (v2.1.217+); routed to the classifier with auto mode available during planning (v2.1.218+) |
| `auto` | Routed to the classifier |
| `dontAsk` | Denied |
| `bypassPermissions` | Allowed |

**`permissions.allow` rules do not pre-approve protected-path writes.** The safety check runs *before* allow rules are evaluated, so `Edit(.claude/**)` in any settings file changes nothing. In prompting modes, a `.claude/` write prompt offers **"Yes, and allow Claude to edit its own settings for this session"**.

**Protected directories:** `.git`, `.config/git`, `.vscode`, `.idea`, `.husky`, `.cargo`, `.devcontainer`, `.yarn`, `.mvn`, and `.claude` — except `.claude/worktrees`.

**Protected files:**

- `.gitconfig`, `.gitmodules`
- Shell startup: `.bashrc`, `.bash_profile`, `.bash_login`, `.bash_aliases`, `.bash_logout`, `.zshrc`, `.zprofile`, `.zshenv`, `.zlogin`, `.zlogout`, `.profile`, `.envrc`
- Package managers: `.npmrc`, `.yarnrc`, `.yarnrc.yml`, `.pnp.cjs`, `.pnp.loader.mjs`, `.pnpmfile.cjs`, `bunfig.toml`, `.bunfig.toml`
- Build: `.bazelrc`, `.bazelversion`, `.bazeliskrc`, `gradle-wrapper.properties`, `maven-wrapper.properties`
- Hooks: `.pre-commit-config.yaml`, `lefthook.yml`/`.yaml`, `.lefthook.yml`/`.yaml`
- Other: `.devcontainer.json`, `.ripgreprc`, `pyrightconfig.json`, `.mcp.json`, `.claude.json`

## 7. Hooks as a permission layer

PreToolUse hooks run **before the permission prompt**, for every tool except `EndConversation`. Output can deny, force a prompt, or skip the prompt.

**Hook decisions do not bypass permission rules.** Deny and ask rules are evaluated regardless: a matching deny blocks the call, and a matching ask still prompts, even when the hook returned `"allow"` or `"ask"`. This preserves deny-first precedence including managed deny rules. Org-`ask` connector tools and `requiresUserInteraction` MCP tools also still prompt.

**But a blocking hook takes precedence over allow rules.** A hook exiting with code 2 stops the call *before* rules are evaluated, so the block applies even when an allow rule would have permitted it.

That asymmetry gives you a clean pattern: **allow `"Bash"` broadly and register a PreToolUse hook that rejects the specific commands you want blocked.** This gets prompt-free operation with precise, programmable exclusions.

## 8. Working directories

Three ways to extend access:

| Method | Persistence |
|---|---|
| `--add-dir <path>` | This session |
| `/add-dir` | This session |
| `permissions.additionalDirectories` | Persistent |

Files in additional directories follow the same rules as the working directory: readable without prompts, editing follows the current mode.

### The configuration-discovery exception table

Adding a directory grants **file access, not a configuration root**. Only these load, and **only from `--add-dir` / `/add-dir`, not from `permissions.additionalDirectories`**:

| Configuration | Loaded from `--add-dir` |
|---|---|
| Skills in `.claude/skills/` | Yes, with live reload |
| Subagents in `.claude/agents/` | Yes |
| Settings | `enabledPlugins` and `extraKnownMarketplaces` keys only |
| CLAUDE.md, `.claude/rules/`, `CLAUDE.local.md` | Only with `CLAUDE_CODE_ADDITIONAL_DIRECTORIES_CLAUDE_MD=1`; `CLAUDE.local.md` also needs the `local` setting source |

Commands and output styles come from the cwd and its parents, `~/.claude/`, and managed settings. **Hooks and other `settings.json` keys load from the cwd's `.claude/` with no parent-directory fallback**, plus user and managed settings. `.claude/settings.local.json` loads from the git repository root as of v2.1.211 (Agent SDK sessions still use the working directory).

To share configuration across projects: user-level files in `~/.claude/`, a plugin, or launching from the directory containing the config.

### `/cd` versus `/add-dir`

`/add-dir` grants access to another directory. `/cd` **relocates** the session: the new directory's CLAUDE.md loads, and `--resume` finds the session from there. Requires v2.1.169+.

## 9. Permissions and sandboxing together

| Layer | Scope |
|---|---|
| **Permissions** | Which tools, which files, which domains. Applies to every tool |
| **Sandboxing** | OS-level enforcement of filesystem and network. **Bash commands and their child processes only** |

How they combine:

- Deny rules stop Claude from **attempting** access
- The sandbox stops Bash from **reaching** resources even if prompt injection bypasses Claude's decision-making
- **Filesystem restrictions merge** `sandbox.filesystem` settings with Read and Edit deny rules into one boundary
- **Network restrictions merge** WebFetch rules with the sandbox's `allowedDomains` and `deniedDomains`

### The auto-allow substitution

With sandboxing enabled and `autoAllowBashIfSandboxed` at its default `true`, sandboxed Bash runs **without prompting even if you have a bare `Bash` ask rule**: the sandbox boundary substitutes for that whole-tool prompt.

**Plan mode skips this substitution** (v2.1.212+). Without an ask rule, read-only commands still run unprompted and anything else prompts while planning, or goes to the classifier when auto mode is available with `useAutoModeDuringPlan` on. With a bare `Bash` ask rule, everything prompts as usual.

Still enforced regardless: content-scoped ask rules like `Bash(git push *)`, explicit deny rules, and the `rm`/`rmdir` circuit breaker on critical paths.

## 10. Managed policy

### Settings precedence

1. **Managed settings** — cannot be overridden by anything, **including command line arguments**
2. Command line arguments
3. `.claude/settings.local.json`
4. `.claude/settings.json`
5. `~/.claude/settings.json`

**If a tool is denied at any level, no other level can allow it.** A managed deny cannot be overridden by `--allowedTools`, a user-level deny blocks a project-level allow, and `--disallowedTools` can add restrictions beyond managed settings.

### Managed-only settings

These have **no effect** outside managed settings:

| Setting | Effect |
|---|---|
| `allowManagedPermissionRulesOnly` | Only managed `allow`/`ask`/`deny` rules apply. **Does not affect the MCP allowlist** |
| `allowManagedMcpServersOnly` | Only managed `allowedMcpServers` respected; `deniedMcpServers` still merges |
| `allowManagedHooksOnly` | Only managed, SDK, and force-enabled-plugin hooks load |
| `allowAllClaudeAiMcps` | Load claude.ai connectors alongside `managed-mcp.json` |
| `allowedChannelPlugins`, `channelsEnabled` | Channel controls |
| `blockedMarketplaces`, `strictKnownMarketplaces` | Marketplace controls |
| `disableSideloadFlags` | Reject `--plugin-dir`, `--plugin-url`, `--agents`, `--mcp-config` at startup |
| `forceRemoteSettingsRefresh` | Block startup until remote settings fetch succeeds; exit on failure |
| `pluginTrustMessage` | Custom text on the plugin trust warning |
| `sandbox.filesystem.allowManagedReadPathsOnly` | Only managed `allowRead`; `denyRead` still merges |
| `sandbox.network.allowManagedDomainsOnly` | Only managed `allowedDomains` and WebFetch allows; non-allowed domains blocked **without prompting** |
| `strictPluginOnlyCustomization` | Block skills, agents, hooks, MCP from user and project sources. `true` locks all four; an array like `["skills", "hooks"]` locks named ones |
| `wslInheritsWindowsSettings` | WSL reads the Windows policy chain in addition to `/etc/claude-code` |

`disableBypassPermissionsMode` is typically managed but **works from any scope**, so a user can lock themselves out.

Note the `disableSideloadFlags` rationale: without it, users bypass `strictKnownMarketplaces` for a single run by passing those flags.

## 11. Workspace trust

`permissions.allow` rules and `permissions.additionalDirectories` in a project's `.claude/settings.json` **grant capability**, so Claude Code applies them only after you accept the workspace trust dialog. Until then it reads but does not apply them. The dialog lists what the folder would grant.

**`deny` and `ask` rules are unaffected**, since they only restrict.

Trust is saved per workspace, keyed on the git repository root, or outside a repository the directory you started from. Starting in your **home directory** holds trust for the session only, never written to disk. **Trusting a parent does not apply a nested project's allow rules.**

### settings.local.json and trust

Usually your own file, so trust does not apply. But **when a repository could have supplied it** — committed to git, or `.claude` is a symlink — its allow rules go through the trust check like project settings.

Claude Code runs git to check whether the repo supplied the file, and **runs that check only in a folder covered by an accepted trust dialog**. So in an untrusted folder, `settings.local.json` allow rules go through the trust check until you accept.

Two exceptions where allow rules apply without trust:

1. The starting directory **is not inside a git repository**
2. The session runs in **your own configuration home**: your home directory, or any directory whose `.claude` you set as `CLAUDE_CONFIG_DIR`

Only the configuration-home exception applies *before* the dialog, because it does not need to run git. A repository-committed `settings.local.json` still requires trust either way.

As of v2.1.200, a workspace whose rules are still unapplied but that never showed the dialog because a parent was trusted shows it on the next interactive start: **"Yes, I trust this folder"** applies rules in the same session, **"No, continue without these permissions"** keeps them ignored and re-asks next session. In `-p` mode no dialog appears and the rules stay ignored.

## 12. Gotchas

1. **Rules are enforced by Claude Code, not the model.** CLAUDE.md shapes intent, never permission.
2. **deny → ask → allow, first match wins.** A deny cannot carry allowlist exceptions, and an ask beats a more specific allow.
3. **A bare tool name in deny removes the tool from context**; a scoped rule leaves it visible and blocks calls. `Bash(*)` behaves like bare `Bash`.
4. **`EndConversation` cannot be removed** while any other tool remains, and never prompts.
5. **Bash approvals persist permanently; file-edit approvals last only until session end.**
6. **The space before `*` is a word boundary.** `Bash(ls *)` and `Bash(ls*)` are different rules.
7. **Environment runners are not stripped wrappers.** `Bash(devbox run *)` permits `devbox run rm -rf .`.
8. **A single leading slash anchors at the settings source, not the filesystem root.** Use `//` for absolute.
9. **`Read(/secrets/**)` in user settings means `~/.claude/secrets/**`**, not your project.
10. **`Edit(src/**)` matches at different depths as an allow versus a deny.**
11. **Only `Edit(path)` and `Read(path)` rules are consulted for file permissions.** `Write(...)`, `Glob(...)`, `NotebookEdit(...)` path rules are accepted and ignored, with a warning.
12. **A `Read` deny also blocks Edit on that path** (v2.1.208+), but not Write or NotebookEdit.
13. **Read and Edit denies do not stop arbitrary subprocesses.** A Python script that opens the file is unaffected. Use the sandbox.
14. **Allow rules require both symlink and target to match; deny rules need only one.**
15. **`WebFetch(domain:*.example.com)` does not match `example.com` itself.**
16. **Parameter matching (`Tool(param:value)`) is deny/ask only**, cannot reach primary content fields, and never matches an omitted parameter.
17. **Unanchored allow globs are silently skipped with a warning** and approve nothing.
18. **Canonical tool names differ from transcript labels.** `Stop Task` is `TaskStop`.
19. **Entering auto mode drops your broad allow rules** for arbitrary code execution.
20. **Auto mode boundaries stated in chat are lost to compaction.** Use a deny rule for guarantees.
21. **`defaultMode: "auto"` is ignored in project and local settings.**
22. **Auto mode ignores subagent `permissionMode` frontmatter.**
23. **`permissions.allow` never pre-approves protected-path writes**, because the check runs first.
24. **A PreToolUse hook cannot override a deny or ask rule, but a code-2 exit does override allow rules.**
25. **`--add-dir` loads skills and agents; `permissions.additionalDirectories` loads nothing.**
26. **You cannot enter `bypassPermissions` mid-session**, and it refuses to run as root outside a recognized sandbox.
27. **Trusting a parent directory does not trust a nested project.**
28. **Managed deny beats `--allowedTools`.** CLI arguments do not outrank managed settings.
