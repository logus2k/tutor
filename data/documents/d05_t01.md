# Configure Claude Projects with Instructions and Knowledge Sources

A **Project** in claude.ai is a dedicated workspace that bundles reusable *custom instructions* and a persistent *knowledge base* so that every conversation inside it starts with the same context. On the Foundations exam, this topic tests whether you understand how to set up a Project correctly, how uploaded knowledge and instructions shape Claude's answers, and how to share a Project with a team without leaking permissions or stale information.

## What a Project is and why it matters

A regular chat is stateless: each new conversation begins with a blank slate, so you re-paste the same background material and re-explain the same rules every time. A Project fixes that. You create it once, give it a name and description, write instructions that apply to all chats inside it, and attach the reference documents Claude should draw on. From then on, every conversation you (or a teammate) start within that Project inherits that setup automatically.

Projects are available to everyone, including free accounts, which can create up to five. To create one, go to claude.ai/projects, click **+ New Project**, and provide a name and description. The description is not decorative — it is a lightweight signal of the Project's purpose and helps teammates find the right workspace.

## Setting custom instructions

Custom instructions are standing guidance that Claude reads before responding in any chat within the Project. You set them by clicking **Set project instructions**. Good instructions define:

- **Role and perspective** — "You are a compliance reviewer for a UK insurance firm."
- **Audience and tone** — "Write for non-technical account managers; plain, concise, no jargon."
- **Constraints and requirements** — "Cite the internal policy document by section; never invent policy numbers."
- **Output preferences** — "Default to a short summary followed by a bulleted action list."

Because these apply to *every* chat in the Project, put durable, workflow-level rules here — not one-off requests. A per-prompt need ("make this particular email shorter") belongs in the individual message, not the Project instructions. Overloading instructions with transient details dilutes the durable guidance and makes the Project harder to maintain.

Note the layering: **profile instructions** (account-wide, set in Settings) apply everywhere; **project instructions** add task-specific context on top for that workspace. When they overlap, project-level guidance is the more specific signal for work done inside the Project.

## Adding knowledge sources

The **knowledge base** appears on the right side of the Project's main page. Click the **+** button to upload documents, text files, and code snippets. As Anthropic's documentation puts it, "anything you upload to this space will be used across all of your chats within that project." This is the difference between attaching a file to one chat (visible only there) and adding it to Project knowledge (visible to every chat in the Project, persistently).

Practical limits matter here. Project files are capped at **30 MB per file**, with no fixed count limit — but the total content must fit within Claude's working capacity. Supported formats include PDF, DOCX, CSV, TXT, and more. For most non-PDF files Claude extracts text only, so a scanned image embedded in a Word document will not be "read."

**RAG mode.** On paid plans, when your project knowledge grows large enough to approach the context-window limit, Claude automatically switches on **retrieval-augmented generation (RAG)** mode. Instead of loading every document in full, Claude retrieves the most relevant passages for each question. This expands how much knowledge a Project can hold, but it changes behavior subtly: Claude sees excerpts, not the whole corpus at once, so precise, well-labeled documents retrieve better than one enormous catch-all file. A common exam-style pitfall is assuming a huge knowledge base guarantees Claude "has read everything" — under RAG it retrieves selectively, and poorly organized sources retrieve poorly.

## How project knowledge shapes responses

When you ask a question, Claude combines your prompt, the Project instructions, and the relevant knowledge sources to produce an answer grounded in *your* material rather than only its general training. This is exactly why Projects are valuable for recurring, context-heavy work: onboarding a new client, drafting against a house style guide, or answering questions from a fixed policy manual.

It is not, however, a guarantee of accuracy. Claude can still produce fluent, specific-looking but wrong details — fabricated citations, invented section numbers — even when a source is attached, and a confident tone is **not** a reliability signal. For compliance or high-stakes audiences, verify factual claims against the authoritative source document yourself before acting or sending. Grounding reduces hallucination risk; it does not eliminate the reviewer's job.

## Sharing a Project with a team

On Team and Enterprise plans you can share a Project with colleagues, and shared Projects appear under the **Shared with me** tab. Two permission levels control what members can do:

- **Can use** — view the contents, knowledge, and instructions, and chat within the Project. This is the right default for most consumers of the workspace.
- **Can edit** — modify the instructions and knowledge, manage members, and actively maintain the Project.

Grant **Can edit** sparingly, because editors can change the shared knowledge and instructions that everyone else relies on. A tempting but wrong move is giving the whole team edit rights "so anyone can fix things" — that invites unreviewed changes and drift in a workspace many people trust. Assign a clear owner or small set of maintainers instead.

One sharing caveat tied to connectors: the Google Drive connector works in the Files section of **private** Projects but is disabled in shared Projects. If a workflow depends on live Drive sync, plan the Project's privacy accordingly.

## Common pitfalls the exam rewards you for avoiding

- **Putting sensitive data in the wrong place.** Apply data-sensitivity controls *before* uploading. Redact or anonymize regulated personal data first; instructing Claude "don't retain this" is not a substitute for a real privacy control.
- **Confusing chat attachments with Project knowledge.** A file added to one chat does not carry across the Project. Upload it to the knowledge base if it should persist.
- **Letting knowledge go stale.** Instructions and files reflect the moment they were written; a Project that is never reviewed will confidently answer from outdated material.
