# Apply Task Decomposition Techniques to Structure Complex Requests

When a request is large or has several moving parts, cramming it into a single prompt usually produces a mediocre result: Claude may skip a step, blur two requirements together, or lose the thread halfway through. Task decomposition is the discipline of breaking a big ask into smaller, ordered sub-tasks so each one gets focused attention. The Foundations exam treats this as a judgment skill — knowing *when* a task needs to be broken up, and *how* to sequence the pieces.

## Why decomposition works

Anthropic's guidance is direct about the failure mode: when a single prompt tries to juggle too many elements, the model can overlook or mishandle parts of the task. Splitting the work into manageable steps raises accuracy and makes the process easier to follow and fix. If something goes wrong, you can see which step produced the problem instead of re-running one giant, opaque request.

There is a human parallel that maps cleanly onto the exam's business framing. You would not hand a new analyst "produce our quarterly board deck" as one instruction. You would say: pull the numbers, then interpret the trends, then draft the narrative, then design the slides. Each hand-off has a checkpoint. Decomposition gives Claude the same scaffolding and gives you the same checkpoints.

## When to decompose (and when not to)

Not every task needs breaking down. A short, single-purpose request — "rewrite this paragraph to sound more formal" — is best left whole; splitting it adds friction for no gain. Decompose when you see one or more of these signals:

- **Multiple distinct deliverables.** The request contains an "and" that hides separate outputs (research *and* an outline *and* a draft).
- **A dependency chain.** Later parts genuinely need the result of earlier parts — you cannot write the recommendation until the analysis exists.
- **Different modes of thinking.** One part is factual gathering, another is creative writing, another is critical review. These benefit from being handled with their own focused instructions.
- **A first attempt that came back thin or muddled.** If a whole-task prompt produced a shallow answer, that is a cue the task was carrying too much at once.

The tempting-but-wrong instinct is to keep adding more requirements onto one ever-longer prompt when results disappoint. Beyond a point that makes things worse, not better; the fix is to divide, not to pile on.

## The core techniques

**Step-by-step within one prompt.** The lightest form of decomposition is asking Claude to work through a task in explicit, numbered stages inside a single request: "First, list the key risks in this contract. Second, rank them by severity. Third, recommend a mitigation for the top three." Ordering the instructions as sequential steps — the docs recommend numbered lists when order or completeness matters — pushes Claude to address each in turn rather than blending them. This is enough for many everyday tasks.

**Prompt chaining across turns.** For heavier work, treat each sub-task as its own turn and feed the output of one into the next. A canonical business chain is *Research → Outline → Draft → Edit → Format*. You review the research before you approve the outline; you approve the outline before Claude drafts. Because you inspect each intermediate result, errors are caught early instead of propagating into a finished-but-flawed deliverable. Anthropic notes that explicit chaining is especially valuable exactly when you want to inspect intermediate outputs or enforce a specific pipeline.

**The self-correction chain.** A particularly powerful pattern is *generate → review → refine*: have Claude produce a draft, then in a fresh step ask it to critique that draft against specific criteria, then have it revise based on the critique. Splitting "write" from "review" gets a more honest evaluation than asking for both in one breath, because the model is not simultaneously defending and judging its own work.

## Sequencing the outputs

Decomposition is not just chopping a task up; it is putting the pieces in a defensible order. Two principles guide the sequence.

First, **gather before you generate.** Facts, source material, and constraints should be established early, because everything downstream depends on them. In the product this often means the first step is having Claude extract and quote the relevant passages from a document before it reasons about them — grounding the later work in the source and reducing invention.

Second, **diverge before you converge.** When a task has an exploratory phase (options, angles, hypotheses) and a decision phase (pick, rank, recommend), do the opening-up first and the narrowing-down second. Forcing a conclusion before the options are on the table produces premature, lower-quality answers.

A practical rule of thumb from prompt-chaining guidance: most effective chains land in the range of a few to a handful of steps. If you find yourself designing many more, that is a signal to combine some steps or to recognize that you are really running two separate projects.

## A worked mini-example

Suppose the ask is: "Analyze our customer churn survey and give leadership a recommendation."

A decomposed approach:

1. **Extract.** "From the uploaded survey responses, pull out every distinct reason customers gave for leaving, quoting the response, and group them into themes." (Grounds the work in real data.)
2. **Quantify.** "Count how many responses fall under each theme and show the ranking." (Turns qualitative material into a picture.)
3. **Interpret.** "For the top three themes, explain the likely business driver and which are addressable in the next quarter." (Reasoning, done after the facts are fixed.)
4. **Recommend and format.** "Draft a one-page memo to leadership with the top three themes, the recommendation for each, and a suggested owner. Professional tone, no invented figures." (The deliverable, built on approved inputs.)

Each step is checkable. If the themes in step one look wrong, you fix them before any recommendation is built on top — far cheaper than discovering the flaw in the finished memo.

## Common pitfalls

- **Over-decomposing trivial tasks**, adding turns and overhead where a single clear prompt would do.
- **Skipping the checkpoints** — chaining only helps if you actually review the intermediate output before moving on; blindly passing it forward re-introduces the errors you were trying to catch.
- **Losing context between turns.** When you chain, make sure each step carries forward what it needs; do not assume Claude remembers an instruction you gave three turns ago unless it is still in view.
- **Sequencing conclusions before evidence**, which produces confident answers unsupported by the source material.

Decomposition, done with judgment, is what turns a sprawling request into a controllable, verifiable process — and knowing when to reach for it is exactly what the exam is checking.
